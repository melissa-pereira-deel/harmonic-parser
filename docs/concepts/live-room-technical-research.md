## What the technology needs to serve

The player arrives in a quiet, moving world and finds a melody by ear. When they return to the motif with a different touch, timing, or bass note, the world should make the change perceptible without making them study the screen. A cue is valuable if it helps them hear something they want to try. The first comparison keeps the artwork fixed and varies the relationship to playing.

The live room is a separate PoC alongside the hosted chord-entry tool and its feedback study. Keep the local room entry relative to the site's base path so a future hosted preview can coexist with the chord page on the GitHub Pages project site. [Chord-page PoC](../2026-11-05-poc-gap-analysis.md) · [Pages workflow](../../.github/workflows/pages.yml)

Run A, B and C as conditions of one scene. Keep sound, instrument, viewport and motion preference consistent within a comparison. An assisted first C session can establish whether a cue belongs in the experience. A separate parser experiment establishes what the system can infer from playing.

## Functional contract to settle first

1. **Arrival and setup.** `/room/` can show the field immediately. Use a separate, keyboard-operable setup view for selecting the study condition and input. The facilitator can start from `/room/?setup=1`, and Escape from the room returns to setup. Request MIDI only after the player selects Connect. A denied, missing, busy or disconnected input should be legible in setup, with replay still available. Start with one selected input and ordinary MIDI access with SysEx disabled. Chrome needs a secure context. Loopback localhost is appropriate for development. Safari currently lacks `requestMIDIAccess` according to browser compatibility data, so it can use replay or drift if its rendering path works. [W3C Web MIDI](https://www.w3.org/TR/webmidi/) · [Browser compatibility data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Navigator.json) · [Chromium Web MIDI](https://www.chromium.org/developers/design-documents/web-midi/)
2. **One event contract.** Live MIDI and fixtures use the same normalized event stream and reducer. Draft event shape uses session-relative monotonic `tMs`, a stable `seq` for ties, and a discriminated payload for note-on, note-off, sustain, or reset. Notes have channel and MIDI pitch, and note-on carries strike velocity. The adapter binds to the selected port and discards messages from a stale connection. Decode velocity-zero note-on as release. Keep physical key state and sustain-held state separate, per channel. For the PoC, represent one active entry per channel and pitch, with a fresh attack on retrigger. Test both note-off forms, ignored messages, pedal release and a reset on input switch, disconnect or tab suspension. A resumed tab starts from a clean held-note state. [W3C Web MIDI input and events](https://www.w3.org/TR/webmidi/#midiinput) · [MIDI Association control changes](https://midi.org/midi-1-0-control-change-messages)
3. **Renderer receives a small frame state.** One clock drives elapsed scene time. Pass bounded strike impulse, register, and a held or decaying envelope to the renderer. A gates gesture influence to zero. B and C consume the same gesture values. Leave visual mapping curves and decay as design variables. Retain a seeded replay path and a sample-at-time capability so agents can inspect fixed frames. Cap pixel ratio and trace history, then measure a Retina-sized window and resizing. A context failure should show the CSS field and a recoverable setup state. Reduced motion can use a quiet field and mild light changes. [WebGL drawing buffer and context](https://registry.khronos.org/webgl/specs/latest/2.0/) · [W3C reduced-motion preference](https://www.w3.org/TR/mediaqueries-5/#prefers-reduced-motion)
4. **Separate cue channel.** A reflection carries display content, `startMs`, a finite duration, an evidence span or note, and origin `facilitated` or `parser`. Allow at most one cue at a time. B and A suppress cue rendering even if a provider emits. In C, compare a fleeting cue with one that holds until the next phrase, one change at a time. A facilitated cue can point to the musical change in ordinary language. Analyst metadata and controls stay in the lab or session notes. The player-facing cue should be available as accessible text if words carry its meaning.
5. **Sound is its own path.** Incoming MIDI reports gestures. It cannot tell us the timbre, loudness or tails of the instrument the player hears. Check that Chrome and the usual sound source can listen to the same keyboard. If a browser voice is needed for the PoC, start it from explicit setup interaction and hold it fixed across conditions. [W3C Web MIDI scope](https://www.w3.org/TR/webmidi/) · [Chrome Web Audio autoplay](https://developer.chrome.com/blog/autoplay#web_audio)

## Where the parser enters

**Existing contract.** `rank(chords)` takes parsed chord symbols. It builds an order-independent profile and returns ranked major/minor key candidates with correlation scores and a chord-relative numeral lookup. Its confidence flags are useful as a description of intent. The underlying thresholds are uncalibrated. A fresh direct probe returned the same ranking for `Am F G C` and `C F G Am`, and a single `C` cleared both checks. The room needs a policy that can withhold a cue even when the ranker has a first choice. [Ranker](../../src/readings.ts#L247) · [Confidence experiment](../../experiments/confidence-thresholds.spike.md)

**Start with two tests of different things.** First, use annotated replay with explicit chord symbols to prove that the real parser can produce candidate readings through a local provider. Play back the events separately and make the output visible in the lab. The chord labels in this path come from the fixture, so label the demonstration accordingly. Second, run a live-input research spike comparing a short-window pitch-class profile with a conservative recognizer for clean held triads. The profile candidate can test whether recent notes provide a plausible tonal center. The triad path can test what is lost when sparse melody or rolled voicings must become chord labels.

**Use the player's material to decide what moves into C.** Compare both routes on short melody, a repeated melody with two bass choices, a rolled or pedalled voicing, a clear chord loop, a deliberately unresolved passage and a change of center. Record the phrase boundaries or ambiguity the player hears, candidate stability, and moments the provider would have spoken or stayed quiet. A useful policy can distinguish thin evidence, poor fit, competing hearings and a usable observation. For example, detecting a new low note beneath a known repeated motif may be more useful than naming a key. A successful chord-fixture demo alone earns a lab result. Promotion to live C requires agreement with listening on the actual material and explicit withholding in thin or unresolved cases. ## Measurement and risks

| Measure | Proposed first check | How to read it |
| --- | --- | --- |
| Gesture timing | In each of B and C, use at least 100 foreground note-on events. Measure handler entry to the first draw submission carrying that event's influence. Start with a p95 target of **33 ms** at 60 Hz. Record actual event count, coalescing and missed responses. In A, verify gesture influence stays zero. | This is a browser-side engineering budget. Hardware and compositor delay require a separate physical check. Keep live and replay figures separate. |
| Frame cadence | In a two-minute foreground run at a documented 60 Hz setting, start with a target of at least **95% of frame intervals within 25 ms**, excluding warm-up and deliberate pauses. Record viewport, pixel ratio, renderer and both idle and active results. | Compare A, B and C on the same machine. If it fails, test a lower pixel budget or simpler field before introducing a heavier renderer. |
| Hardware path | Player tries initial permission, first strike, soft/hard strike, pedal release, unplug/replug, and the usual audio route on the target laptop. | Confirm the behavior feels attached to the hand. A virtual source can check state and routing. Physical response and feel come from this session. |
| Musical usefulness | Compare the three conditions on the player's motif. Mark one variation worth keeping, cue interpretation, and what the player played next. Note any interrupted phrase. | A/B/C are early qualitative comparisons. Keep facilitator and parser evidence separate and repeat with another motif or session before making a durable decision. |

The existing **27.6 ms p95** measures synthetic typed input to a second animation-frame callback on the current chord page. It is useful as precedent for measuring a user-visible path. The new targets above are working budgets for this study. [Existing latency experiment](../../experiments/render-latency.spike.md)
